# Agent Join Codes — Decision Record

**Date:** 2026-09-24
**Branch:** `feat/agent-join-codes
**Spec:** [agent-join-codes.md](agent-join-codes.md)

Every judgement call made while executing the implementation plan, in the order made.
These were decided without checking in, so that execution could run unattended; each
records its reasoning and what it costs if the call was wrong. Reworking any of them
is a normal change, not a rescue.

1. corrected T1's normalize assertion to "001111VV" — the asserted value was arithmetically impossible under the implementation the same task specifies, and would have failed Task 1 into a fix loop for a plan defect rather than an implementation defect — if wrong, the substitution table is what's wrong instead, and the test will catch it.

2. converted T5's mockSearch to vi.hoisted — vi.mock factories are hoisted above plain let bindings and throw on access; cost if wrong is nil, the mock behaves identically.

3. added a canViewJoinCode guard to T7's card so it renders nothing for AGENT/STAFF and skips the fetch — the backend already denies them, so the only thing the card could add for those roles is a confusing error toast; if wrong, a market center wanted staff to read the code and the guard is a one-line widening.

4. fix rotate() atomicity — the finding is correct and the defect is MINE, not the implementer's: I wrote the two-statement rotate into the plan verbatim. The spec's binding invariant is "one live code per market center". The partial unique index prevents two rows, but an INSERT failing after the UPDATE commits leaves ZERO active codes, locking every agent out of joining until someone re-rotates. withTransaction already exists (backend/ticket/db.ts:44) and Task 3 already uses it, so this is consistency with the codebase, not new machinery. Cost if wrong: a transaction wrapper around a two-statement write is near-zero risk.

5. park the concurrent-rotate raw unique-violation as a deferred minor — the atomicity fix removes the zero-code window but two admins rotating the same market center simultaneously still makes the loser's INSERT raise a constraint error. No corruption is possible (the index holds), the case is rare, and the loser can retry. Cost if wrong: one admin sees a 500 instead of a friendly message; a catch-and-retry is additive later.

6. the coverage finding is valid but its original wording is not achievable at this layer, so I am retargeting it rather than repeating it. The backend suite mocks the database, so "exactly one active row exists" cannot be proven by a unit test — that invariant is enforced by the partial unique index in the migration, not by application code. What IS provable here, and what round 2 must assert: the UPDATE deactivates the prior active row, the INSERT carries the right parameters, UPDATE precedes INSERT inside one transaction, and a failing INSERT rejects. Cost if wrong: if I have misjudged what the harness can express, the tests still improve on mock-call assertions and the DB-level invariant remains index-enforced either way.

7. dispatched this task's review on opus rather than the sonnet used for tasks 1-2 — this is the tenancy-assignment code, where the whole feature's risk concentrates, and a miss here puts a stranger inside another brokerage. Cost if wrong: one more expensive review seat.

8. accept Important #1 (TOCTOU). The guard reads market_center_id, then the UPDATE is unconditional, so two concurrent requests bearing codes for two DIFFERENT market centers both pass and both junction inserts succeed — ON CONFLICT never fires because the market_center_id differs. The agent ends up with two brokerages in their /users/me switcher. That is precisely the tenant-boundary failure this task exists to prevent, and it came from my plan. Fix: make the UPDATE its own gate (WHERE ... AND market_center_id IS NULL AND is_active = true RETURNING id). Cost if wrong: a conditional UPDATE is strictly safer than an unconditional one.

9. accept Important #2 (double submit). My plan's test named "makes a double submit idempotent" never submits twice — it asserts a string appears in SQL. Same mock-theater failure mode that cost Task 1 two rounds, authored by me. The real behavior duplicates the history row and re-notifies every admin. The #1 guarded UPDATE fixes the behavior; the test must actually invoke the handler twice. Cost if wrong: none, the test gets stronger.

10. accept Important #3 (post-commit calls unretriable) but keep the placement. The spec lists notification preferences among the writes that must not partially apply; my plan put them after the transaction with a comment claiming they are "safe to retry". That claim is false — the already-a-member guard blocks the retry, so a post-commit throw strands the user joined but half-provisioned with no self-service recovery. Making the helper transaction-aware is a larger change than this task should carry, and getUserContext already ensures preferences on both user-creation branches, so the call is near-defensive anyway. Fix: wrap both post-commit calls in try/catch and log, so a committed join always returns 200. This is a DELIBERATE, RECORDED deviation from the spec's four-writes-atomic wording. Cost if wrong: a rare preferences failure is logged rather than surfaced, and the user is joined correctly either way.

11. accept Important #4 (tests discard interpolated values). My executedSql() helper maps each call to call[0].join("?"), keeping only template strings, so nothing in 9 tests pins WHICH market_center_id is written. On a task whose whole purpose is placing a user in the correct tenant, that is the one value the tests must pin. Cost if wrong: none.

12. fold Minor #1 (normalization asserted nowhere) into this fix round rather than deferring. The repository mock returns for any argument, so deleting normalizeJoinCode breaks hyphenated and lowercase entry in production while all 9 tests still pass. It is the same "test named for a property it does not verify" class as #2, it is one assertion, and the file is already being edited — folding it in does not extend the loop. Cost if wrong: one extra line in a test.

13. NO CODE CHANGE for the Important finding (STAFF_LEADER can trigger a write via mint-on-first-read). I am ruling on the merits, not deferring to the plan. The spec restricts ROTATION to ADMIN because rotation REVOKES the outstanding code and breaks every join link already in circulation. Minting the first code revokes nothing — there is no prior code — so it is initialization, not rotation, and the destructive act the ADMIN gate exists to protect is absent. Blocking it would mean a staff leader who opens settings before any admin ever has sees a card they cannot populate. The code minted is one they are already permitted to read. Cost if wrong: a market center wanted first-code creation to be an admin-only ceremony; gating the mint branch is then a two-line change.

14. accept Important #1 (code divergence in the in-flight GET window) and fix it by LOCKING the resolved code, not merely disabling the input. My plan derives join()'s code from the same mutable state the input writes to, so the confirmed name and the submitted code can diverge — the screen says "joining A" while the POST joins B. Disabling the input closes the one currently reachable window; storing the code that was actually resolved eliminates the whole class, and costs one piece of state. Cost if wrong: none, it is strictly narrower than the current behavior.

15. accept Important #2 (resolveCode never checks response.ok). My plan branches only on data?.valid, so an infra failure that returns parseable JSON without a valid field is reported to the agent as "that join code isn't valid" — sending them to argue with their market center about a code that is fine. join() already checks response.ok; resolve must match. Cost if wrong: none.

16. accept Important #3 (signed-out round trip has zero tests). This is the PRIMARY user path — an agent who does not yet have an account — and neither my four tests nor the implementer's fifth ever sets isSignedIn:false, so the SignUp branch and its redirect URLs are entirely unexercised. The reviewer also established the return lands on the entry step rather than the confirmation step, requiring a second Continue click. That is acceptable behavior, but it must be pinned by a test so it cannot silently become a dead end. Cost if wrong: the extra click is mildly clunky; a test that documents it is still correct.

17. reject the eslint-disable and fix it properly, in two parts. (1) Use the latest-ref pattern so the effect depends only on real inputs (marketCenterId, canViewJoinCode) and never on a third-party function identity. This is correct whether or not Clerk's getToken is stable — and I am not willing to bet the settings page on an assumption about a third-party hook's identity, because if it is NOT stable the current arrangement is an infinite refetch loop in production, not just in tests. (2) Make the mock return a stable getToken via vi.hoisted, so the test reflects production instead of manufacturing a loop, and add a test asserting exactly one fetch on mount so the loop property is pinned rather than rediscovered. Cost if wrong: the ref indirection is marginally more code than a dependency array that happens to work.

18. rotate() may keep reading the destructured getToken rather than the ref. The implementer asked. rotate is only invoked from a click handler, never as an effect or callback dependency, so it carries no re-render-loop exposure, and reading the current render's value inside an event handler is idiomatic React. Forcing it through the ref for symmetry would add indirection without removing any risk. Cost if wrong: none identified.

19. accept the pop-in, no change. The sibling card on the same settings page, auto-close-settings.tsx:127, gates on exactly the same derived boolean (role === STAFF_LEADER || role === ADMIN) with no loading state, so this matches established behavior on this page rather than introducing a new inconsistency. Rendering a skeleton for one card and not its neighbour would look more broken, not less. Cost if wrong: a skeleton is additive and local.
